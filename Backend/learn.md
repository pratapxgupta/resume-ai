# Backend Learning Guide

This document explains how the backend is organized, what every project file does, and how each API route works. The backend is an **Express.js REST API** that stores users in **MongoDB** and uses **JWT tokens in cookies** for authentication.

## 1. Folder structure

```text
Backend/
|-- server.js
|-- package.json
|-- package-lock.json
|-- node_modules/
|-- learn.md
`-- src/
    |-- app.js
    |-- config/
    |   `-- database.js
    |-- routes/
    |   `-- auth.routes.js
    |-- controllers/
    |   `-- auth.controller.js
    |-- middlewares/
    |   `-- auth.middleware.js
    `-- models/
        |-- user.model.js
        `-- blacklist.model.js
```

### What each folder is for

| Folder | Purpose |
|---|---|
| `src/config` | Configuration code, such as connecting the application to MongoDB. |
| `src/routes` | Defines API URLs and connects each URL to middleware and a controller. |
| `src/controllers` | Contains the main request-handling logic. Controllers read requests, use models, and send responses. |
| `src/middlewares` | Contains functions that run before a controller. The current middleware checks authentication. |
| `src/models` | Defines the shape of MongoDB documents and provides methods for querying the database. |
| `node_modules` | Installed npm packages. It is generated by `npm install` and should not be edited manually. |

## 2. How a request moves through the project

For a request such as `GET /api/auth/get-me`, the flow is:

```text
Client request
    -> server.js starts the server
    -> src/app.js matches the /api/auth prefix
    -> routes/auth.routes.js matches /get-me
    -> middlewares/auth.middleware.js verifies the token
    -> controllers/auth.controller.js gets the user
    -> models/user.model.js queries MongoDB
    -> JSON response is returned to the client
```

The route file decides **which function runs**. The controller decides **what the endpoint does**. The model decides **how data is stored or retrieved**. Middleware performs reusable checks before the controller runs.

## 3. Root files

### `server.js`

This is the backend's entry point.

It performs these steps:

1. `require("dotenv").config()` loads environment variables from a `.env` file into `process.env`.
2. It imports the Express application from `src/app.js`.
3. It imports and calls `connectDB()` to connect to MongoDB.
4. It starts the HTTP server on port `3000`.

Current server address:

```text
http://localhost:3000
```

Important note: `connectDB()` is called without `await`, so the server can begin listening before the database connection finishes. A more robust application normally waits for a successful database connection before accepting requests.

### `package.json`

This file contains project metadata, npm scripts, and dependency names.

The development command is:

```bash
npm run dev
```

It starts `server.js` through Nodemon. Nodemon automatically restarts the server after source-code changes.

Main dependencies:

| Package | Purpose |
|---|---|
| `express` | Creates the HTTP server, routes, middleware chain, requests, and responses. |
| `mongoose` | Connects Node.js to MongoDB and provides schemas/models. |
| `bcryptjs` | Hashes passwords and compares login passwords with stored hashes. |
| `jsonwebtoken` | Creates and verifies JWT authentication tokens. |
| `cookie-parser` | Reads cookies and makes them available through `req.cookies`. |
| `dotenv` | Loads secrets and configuration from `.env`. |
| `nodemon` | Restarts the server during development when files change. |

### `package-lock.json`

This file records the exact installed dependency versions. It makes installations consistent across machines. npm manages it automatically; it should normally be committed but not edited by hand.

## 4. Application setup

### `src/app.js`

This file creates and configures the Express application.

```js
const app = express()
```

The application uses two global middleware functions:

- `express.json()` parses a JSON request body and places its data in `req.body`.
- `cookieParser()` parses request cookies and places them in `req.cookies`.

It then imports the authentication router and mounts it at:

```text
/api/auth
```

Therefore, a route written as `/login` inside `auth.routes.js` becomes `/api/auth/login` in the final API.

The file exports `app` instead of starting the server itself. This separation makes the application easier to test and keeps startup logic in `server.js`.

## 5. Database configuration

### `src/config/database.js`

The `connectDB()` function connects Mongoose to MongoDB using:

```js
mongoose.connect(process.env.MONGO_URI)
```

The MongoDB URL must be supplied through the `MONGO_URI` environment variable.

Current issue: the `catch` block declares `error` but logs `err`. If the connection fails, `err` is undefined and can cause another error. It should log `error`.

## 6. Models

### `src/models/user.model.js`

This model represents a user in the MongoDB `users` collection.

| Field | Type | Meaning |
|---|---|---|
| `username` | String | Public username; intended to be unique. |
| `email` | String | Login email; intended to be unique. |
| `password` | String | Bcrypt password hash, not the original password. |

The model is used by controllers through methods such as:

- `userModel.findOne(...)` to find a user.
- `userModel.findById(...)` to find a user by MongoDB ID.
- `userModel.create(...)` to save a new user.

Important notes:

- The email field uses `require: true`, but the correct Mongoose option is `required: true`. At present, Mongoose may not enforce the email requirement at the schema level.
- `unique` creates a uniqueness index; it is not a complete validation strategy. Duplicate-key database errors should still be handled.
- Passwords are hashed in the register controller before being stored.

### `src/models/blacklist.model.js`

This model stores JWTs that have been logged out. Its MongoDB collection is `blacklistTokens`.

| Field | Type | Meaning |
|---|---|---|
| `token` | String | A JWT that should no longer be accepted. |
| `createdAt` | Date | Added automatically because `timestamps: true` is enabled. |
| `updatedAt` | Date | Added automatically because `timestamps: true` is enabled. |

Why a blacklist is needed: clearing a browser cookie removes the token from that browser, but the JWT itself remains cryptographically valid until it expires. Saving it in the blacklist allows the authentication middleware to reject it immediately.

The current blacklist has no automatic cleanup. Because tokens expire after one day, a production version could use a MongoDB TTL index to delete old blacklist entries.

## 7. Authentication middleware

### `src/middlewares/auth.middleware.js`

The exported `authUser` middleware protects private routes.

Its process is:

1. Read `req.cookies.token`.
2. Return `401 Unauthorized` if the cookie is missing.
3. Search the blacklist collection for the token.
4. Return `401 Unauthorized` if the token was blacklisted during logout.
5. Verify the token signature using `process.env.JWT_SECRET`.
6. Put the decoded JWT payload in `req.user`.
7. Call `next()` so the next middleware/controller can run.

The token payload created by this project looks like:

```json
{
  "id": "MongoDB user ID",
  "username": "the username",
  "iat": 0,
  "exp": 0
}
```

`iat` and `exp` are automatically added by the JWT library. The token expires after one day.

The controller after this middleware can use `req.user.id` because the middleware attached the decoded payload to the request.

## 8. Route file

### `src/routes/auth.routes.js`

This file creates an Express router for authentication endpoints. Its final base URL is `/api/auth` because that prefix is added in `src/app.js`.

| Method | Final URL | Access | Middleware | Controller |
|---|---|---|---|---|
| POST | `/api/auth/register` | Public | None | `registerUserController` |
| POST | `/api/auth/login` | Public | None | `loginUserController` |
| GET | `/api/auth/logout` | Public | None | `logoutUserController` |
| GET | `/api/auth/get-me` | Private | `authUser` | `getMeController` |

“Public” means no authentication middleware is required. “Private” means the request must contain a valid, non-blacklisted JWT cookie.

Route syntax example:

```js
authRouter.get("/get-me", authMiddleware.authUser, authController.getMeController)
```

Express runs those arguments from left to right: match `/get-me`, execute `authUser`, and only execute `getMeController` if the middleware calls `next()`.

## 9. Controllers and endpoint notes

### Register: `POST /api/auth/register`

Controller: `registerUserController`

Purpose: create a new account, automatically log the new user in, and return safe user information.

Request body:

```json
{
  "username": "pratap",
  "email": "pratap@example.com",
  "password": "strong-password"
}
```

Process:

1. Read `username`, `email`, and `password` from `req.body`.
2. Return status `400` if a required value is missing.
3. Search MongoDB for the same username or email.
4. Hash the password using bcrypt with 10 salt rounds.
5. Create the user in MongoDB.
6. Sign a JWT containing the user's ID and username.
7. Store the JWT in a cookie named `token`.
8. Return status `201 Created` and the new user's safe fields.

Success response shape:

```json
{
  "message": "User register successfully",
  "user": {
    "id": "user-id",
    "username": "pratap",
    "email": "pratap@example.com"
  }
}
```

Current issue: the duplicate-user branch calls `res.stats(400)`. Express uses `res.status(400)`. If a duplicate account is found, the current code will throw an error instead of returning the intended response.

### Login: `POST /api/auth/login`

Controller: `loginUserController`

Purpose: verify a user's credentials and issue an authentication cookie.

Request body:

```json
{
  "email": "pratap@example.com",
  "password": "strong-password"
}
```

Process:

1. Find a user by email.
2. Return `400` with a generic error if the user does not exist.
3. Compare the supplied password with the stored bcrypt hash.
4. Return `400` with the same generic error if the password is incorrect.
5. Create a JWT that expires in one day.
6. Set it as the `token` cookie.
7. Return status `200 OK` and safe user fields.

Using the same error for an unknown email and a wrong password avoids revealing which email addresses have accounts.

### Logout: `GET /api/auth/logout`

Controller: `logoutUserController`

Purpose: invalidate the current token and clear the authentication cookie.

Process:

1. Read the `token` cookie.
2. If it exists, save it in the blacklist collection.
3. Clear the `token` cookie in the response.
4. Return status `200 OK`.

This route currently succeeds even when no token was provided. It is marked public and does not use `authUser`.

Design note: logout changes server state by creating a blacklist record, so `POST /logout` is usually more REST-appropriate than `GET /logout`.

### Current user: `GET /api/auth/get-me`

Middleware: `authUser`

Controller: `getMeController`

Purpose: return the database record for the currently authenticated user without returning the password.

Process:

1. `authUser` verifies the JWT cookie and sets `req.user`.
2. The controller reads `req.user.id`.
3. `userModel.findById(...)` retrieves the latest user data from MongoDB.
4. The controller returns the ID, username, and email.

No request body is needed, but the request must include the `token` cookie.

## 10. Required environment variables

Create a `.env` file inside `Backend/` with values in this form:

```env
MONGO_URI=mongodb://127.0.0.1:27017/resume-ai
JWT_SECRET=replace-with-a-long-random-secret
```

- `MONGO_URI` tells Mongoose which MongoDB database to use.
- `JWT_SECRET` signs and verifies authentication tokens. It must remain private and should be long and unpredictable.

Do not commit a real `.env` file or secret to source control.

## 11. Running and testing the backend

From the `Backend` folder:

```bash
npm install
npm run dev
```

MongoDB must be reachable through `MONGO_URI`. The API then listens on port `3000`.

When testing with Postman or another API client:

1. Register or log in.
2. Allow the client to store the `token` response cookie.
3. Send that cookie with `/get-me` and `/logout` requests.

If a browser frontend runs on another origin or port, the backend will also need CORS configuration, and frontend requests must enable credentials so cookies are sent.

## 12. Authentication and security notes

The current project demonstrates the authentication flow, but production code should also consider:

- Set cookie options such as `httpOnly: true`, `secure: true` in HTTPS production, and an appropriate `sameSite` value.
- Validate and normalize email, username, and password input.
- Add a centralized error-handling middleware so database/JWT errors return controlled responses.
- Handle duplicate-key errors from MongoDB.
- Add rate limiting to login and registration routes.
- Store only necessary data in JWT payloads.
- Remove expired blacklist entries.
- Configure CORS when the frontend and backend use different origins.
- Use a configurable `PORT` instead of permanently fixing port `3000`.

## 13. Current code issues summary

These notes describe the repository as it currently exists; they are not changes made by this document.

| File | Current code | Effect | Intended correction |
|---|---|---|---|
| `auth.controller.js` | `res.stats(400)` | Duplicate registration throws an error. | Use `res.status(400)`. |
| `database.js` | `catch (error)` then `console.log(err)` | A failed connection references an undefined variable. | Log `error`. |
| `user.model.js` | `require: true` on email | Email requirement may not be enforced by Mongoose. | Use `required: true`. |
| `server.js` | Calls `connectDB()` without awaiting it | Server may accept traffic before MongoDB connects. | Await connection before `app.listen`. |
| Cookie creation | `res.cookie("token", token)` only | Cookie lacks recommended production security options. | Add suitable `httpOnly`, `secure`, and `sameSite` options. |

## 14. Quick mental model

- **`server.js`** starts everything.
- **`app.js`** configures Express and mounts routers.
- **Routes** map HTTP method + URL to functions.
- **Middleware** checks or prepares a request before its controller.
- **Controllers** contain endpoint behavior.
- **Models** communicate with MongoDB.
- **JWT** proves which user made a request.
- **Cookie** transports the JWT between client and server.
- **Blacklist** invalidates a JWT before its expiration time.
